## 概要

すべての変更を読み取り、論理的にまとまりのある単位へグループ化。コミット対象の範囲と計画（分割・メッセージ・順序）をユーザーに確認してから、コミットとプッシュをセットで実行する。

git 操作はすべてこの場で自分の Bash ツールで実行する。サブエージェント（Agent ツール）は呼び出さない。

## 手順

### 1. 差分確認

以下を並列で実行して状態を把握する：
- `git status --short` — 全ファイルの状態（ステージング済み・未ステージング・未追跡）
- `git diff --staged` — ステージング済みの差分
- `git diff` — 未ステージングの差分
- `git log --oneline -10` — 直近のメッセージ慣例（type/scope）の参考

未追跡ファイルは必要に応じて Read で内容を確認する。

**変更が何もない場合**: 「コミットする変更がありません」と伝えて終了する。

### 2. 対象範囲の確認

**AskUserQuestion ツール**で対象範囲を確認する：

```
question: "コミット対象の範囲を確認してください。\n\n<git status の要約（ステージング済み/未ステージング/未追跡の内訳）>"
header: "対象範囲"
options:
  - label: "全部対象にする"
    description: "ステージング済み・未ステージング・未追跡をすべてコミット対象にする"
  - label: "ステージング済みのみ"
    description: "現在ステージングされている変更のみコミットする"
  - label: "キャンセル"
    description: "処理を中断する"
```

- ステージング済みの変更が存在しない場合は「ステージング済みのみ」を提示しない
- Other で個別のファイル・範囲指定も受け付ける
- この時点では git add は実行しない

### 3. 論理単位への分割とメッセージ作成（日本語）

対象の差分を精査し、**日本語**の Conventional Commits メッセージとともに論理的なグループへ分割する。

**分割は無理に行わない。** 1つのスコープ・関心事にまとめられるなら1コミットでよい。分割するのは、異なる関心事が混ざっていて分けた方が履歴が読みやすくなる場合のみ。迷ったらまとめる。

**グループ化の基準（優先順位順）:**
1. 同一機能・同一コンポーネントの変更は1つにまとめる（例: `hyprland/ashell.nix` と `hyprland/default.nix` への同一機能追加）
2. type が異なる変更は別グループにする（例: `feat` と `chore` は分ける）
3. 完全に独立した機能は別グループにする
4. 変更量が多くても論理的に1つのまとまりなら1グループで構わない

**順序の決定:** 複数コミットに分ける場合は、依存関係・時系列を考慮して順序を決める。先に存在しているべきものを先にコミットする（例: パッケージの追加 → その設定ファイルの追加、モジュールの定義 → それを import する変更）。各コミット直後の状態が単体で筋の通ったリポジトリになることを意識する。

**メッセージ形式**: `type(scope): 説明`

typeの選び方：
- `feat` — 新機能の追加
- `fix` — バグ修正
- `chore` — ビルド・依存関係・設定の変更
- `refactor` — 動作変更を伴わないコードの整理
- `docs` — ドキュメントのみの変更
- `style` — フォーマットのみの変更
- `test` — テストの追加・修正

scopeの選び方（このリポジトリの慣例）：
- `nvim`, `zsh`, `git`, `starship` などプログラム名
- `home`, `os` など設定の対象
- 複数にまたがる場合は scope を省略可

### 4. コミット計画の確認（順序含む）

分割案を順序どおりの一覧で表示し、**AskUserQuestion ツール**で確認を取る。グループが1つの場合も確認は行う。

表示例（テキストで整形して question に含める）：
```
コミット 1/2: feat(home): fish シェルを追加
  対象: home/programs/fish.nix, home/common.nix

コミット 2/2: feat(os): ログインシェルを fish に変更
  対象: os/common.nix
```

```
question: "以下の順序でコミットし、完了後そのままプッシュします。\n\n<上記の分割案>\n\nよいですか？"
header: "コミット計画"
options:
  - label: "承認"
    description: "この計画でコミットとプッシュを実行する"
  - label: "修正"
    description: "計画を変更する（Otherでグループ変更・メッセージ修正・順序入替などを指示）"
  - label: "キャンセル"
    description: "処理を中断する"
```

- **承認**: ステップ5へ
- **修正**: 指示に従って計画を修正し、再度このステップから確認を取る
- **キャンセル**: 中断する

### 5. 実行（コミット＆プッシュ）

承認済みのため追加の確認は行わず、コミットとプッシュをセットで実行する（プッシュの個別確認はしない）。

1. **英語への翻訳**: 各メッセージを英語の Conventional Commits に翻訳する（このリポジトリのコミット履歴は英語）。`type(scope):` は保持し、説明文は直訳ではなく慣用的な英語にする。
   例: `feat(hyprland): noctalia テーマを追加` → `feat(hyprland): add noctalia theme`
2. **ステージングのリセット**: 複数コミットに分ける場合は `git reset HEAD -- .` でステージングを一旦リセットする（ワーキングツリーは変更しない）。1コミットのみなら不要。
3. **順番にコミット**: 承認された順序どおりに、各グループの対象ファイルを `git add <files>` → `git commit -m "<英語メッセージ>"` する。
4. **プッシュ**: `git push`。上流ブランチ未設定なら `git push -u origin <現在のブランチ名>`。

途中でコミットやプッシュが失敗した場合はそこで停止し、失敗内容とその時点の状態（何コミット目まで完了したか）を報告する。

完了したら `git log --oneline -<コミット数>` の結果とプッシュ結果を表示して終了する。
